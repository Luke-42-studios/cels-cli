## Key Findings

### What Developers Face Today (No CLI)
1. Must clone CELS repo and manually write CMakeLists.txt with FetchContent blocks
2. Must discover modules by browsing GitHub (no catalog/registry)
3. Must manually add git submodules for each module
4. Must know system dependency names (ncurses-dev, etc.)
5. Build via custom shell script (run.sh) — not portable

### Package Management Gaps
- No module discovery mechanism (modules scattered across GitHub repos)
- No dependency resolution (transitive deps are manual)
- No lock file or reproducibility beyond FetchContent GIT_TAG pins
- No backend switching command (`cels add --backend sdl3`)
- No module authoring scaffold

### Dependencies on CELS Core
- **Backend Abstraction (Phase 7)**: `--backend tui` flag needs the `-DCELS_BACKEND` CMake variable from Phase 7
- **CEL_Remember (Phase 6)**: SDK examples should demonstrate CEL_Remember once available
- CLI can begin implementation of `cels init` and `cels build` now; backend selection waits for Phase 7

### Technology Stack (2026-02-09 — REVISED)
- **Scrapped:** TypeScript/Pastel/Ink approach (overkill, wrong ecosystem)
- **New approach:** CELS ncurses TUI app (built with CELS itself)
- Runtime: Native C binary (no Node.js/Python dependency for end users)
- Distribution: npx with prebuilt platform-specific binaries (like esbuild/turbo)
- TUI: cels-ncurses (same as cels-debug)
- Blocked on: CELS core Phase 7 (Backend Abstraction Interface)

### Priority Order
1. `cels init` — project scaffolding (can start now)
2. `cels build` / `cels run` — build orchestration (can start now)
3. `cels add` / `cels remove` — thin wrapper: writes `cels_require()` lines to CMakeLists.txt
4. `cels link` / `cels unlink` — local development support (writes `cels_local()` lines)
5. `cels update` — pulls latest CelsDeps.cmake from CELS core (updated registry + tags)
6. `cels doctor` — environment health check
7. `cels init --backend X` — backend selection (needs CELS Phase 7)
8. TUI dashboard — module browser (after core commands work)

### Architecture Simplification (2026-02-08)
The dependency system is now CMake-native via `CelsDeps.cmake` in CELS core:
- `cels_require(name)` — fetch + resolve transitive deps + link
- `cels_local(name path)` — local override for framework developers
- `cels_register(name URL url TAG tag ...)` — custom module support

This eliminates the need for:
- JSON/TOML manifest files (cels-module.json)
- Custom dependency resolver in TypeScript
- Module registry server or static registry.json
- Complex CMake AST manipulation

The CLI becomes a **thin convenience wrapper** around these CMake functions.
